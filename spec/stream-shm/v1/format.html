irTactile Shared-Memory Stream

Binary format & protocol - version 1.0 · kMagic = 0x41535449 ("ITSA") · little-endian throughout · IEEE-754 float32 · two's-complement int16 · all fields naturally aligned, no packing.
The normative text is the spec tree - spec/stream-shm/v1/fields.md, README.md and spec/common/; this page is a visual map of it. Offsets are pinned in bindings/cpp/include/irtactile/shm/stream/layout.h.

1 · Segment layout at a glance

A stream lives in one named shared-memory segment. Its bytes, from offset 0:

ShmStreamHeader
256 B
slot array - ringBlocks × slotBytes
trailing pad
to totalBytes
offset 0  ·  header at offset 0 is 64 KB-aligned by the OS mapping, so its 64-byte alignment survives into the view  ·  slotArrayOffset = 256 (align64 of the header)  ·  access-class breakdown within the header, including producerPid at 224, is shown in the byte grid below

totalBytes is the size class, not the live footprint. The live layout ends at slotArrayOffset + ringBlocks × slotBytes; everything from there to totalBytes is unused producer-zeroed padding. A consumer bounds-checks against totalBytes (itself checked against the real mapped size) and never assumes the two are equal.

Each slot is a self-describing block: a 64-byte descriptor followed by one contiguous plane per channel, padded to a multiple of 64 so a slot being written never shares a cache line with a slot being read:

ShmBlockDesc64 B
plane ch 0channelPlaneBytes
plane ch 1channelPlaneBytes
… ch N−1channelPlaneBytes
padto ×64 B

Normative addressing arithmetic

slot_index   = seq % ringBlocks
slot_base    = base + slotArrayOffset + slot_index × slotBytes
descriptor   = slot_base                                  // ShmBlockDesc
plane(ch)    = slot_base + slotPayloadOffset + ch × channelPlaneBytes
sample(ch,i) = plane(ch) + i × bytesPerSample             // i < samplesPerBlock
Every published block is full. There is no per-block sample count. A block carries exactly header.samplesPerBlock samples per channel; a producer that cannot finish one abandons it (the slot stays at kSlotBusy) and charges the partial fill to the next block's firstSampleIndex, so the loss appears in your gap_samples. Validate the bound once, at attach - samplesPerBlock × bytesPerSample <= channelPlaneBytes - and every block is then in bounds by construction; the per-block layoutEpoch also guarantees the payload was written under the geometry you validated. Do not take a loop bound from anywhere else.
Every quantity above is a byte offset from base, and every one of slotArrayOffset, slotBytes, slotPayloadOffset, channelPlaneBytes is read from the header, never recomputed. A consumer that re-derives them works until a future version pads differently - then it walks into the middle of a slot with no error anywhere.
Plane alignment is weaker than the slot's. Plane 0 is always 64-aligned (because the slot is), but every plane after it is aligned to whatever channelPlaneBytes divides by - as little as 4 bytes. Planes are guaranteed bytesPerSample-aligned and nothing more. That is exactly enough for the typed view every binding builds (const float*, Rust's slice::from_raw_parts::<f32>, MemoryMarshal.Cast, a NumPy view) - and not enough for an aligned SIMD load, so use unaligned loads. Because a typed view's soundness rests on it, the guarantee is validated at attach, not assumed: every term of the plane address - slotArrayOffset, slotBytes, slotPayloadOffset, channelPlaneBytes - must be a multiple of bytesPerSample, and a header violating that is rejected as malformed.

2 · ShmStreamHeader - 256 bytes

The header splits into three access classes:

  • bytes [80, 112) - the only concurrently written fields. Read directly, per field, with acquire loads.
  • pinned - magic, versionMajor, headerBytes, totalBytes, slotArrayOffset. A rewrite MUST NOT change these: consumers map once, blind, against them and never remap, and a Win32 segment cannot grow. Changing one requires a different segment, and therefore a different name.
  • layout - stream configuration and addressing fields. Protected by the layoutSeq seqlock; a producer restart may rewrite them in place.

OffsetSizeFieldTypeMeaning

producerPid - diagnostics only, never load-bearing

The process id of the producer that last (re)wrote the header, stored under the same layoutSeq rewrite that stamps the identity strings. It answers one question: is the process that owns this segment still alive? - which makes zombie adjudication (a segment left behind by a crashed producer, kept alive by a consumer's open handle) deterministic instead of purely staleness-based.

PIDs are reused by every OS. A liveness verdict may treat "PID no longer names a running process" as proof of abandonment, but never the converse: producerPid alive says nothing by itself, and it must always be combined with the deviceState / lastPublishQpc staleness rules. It is not a substitute for them, and no addressing or timing behaviour may ever derive from it.

3 · ShmBlockDesc - 64 bytes

Sits at the base of every slot. The descriptor's seq is both the block's identity and the slot's lock word.

Hover or click a field to inspect it.
OffsetSizeFieldTypeMeaning
kSlotBusy = 0xFFFFFFFFFFFFFFFF is stored in seq for the whole time the producer is filling the slot, and replaced by the real block index on publish. It is load-bearing, not cosmetic: at ringBlocks = 2 the slot a reader is copying is the very next one the writer claims. The invalidating store, published before the first sample of the new block lands, is what stops a preempted reader from re-checking the descriptor, finding the previous block's seq still there, and returning torn data.

4 · Ring protocol - interactive

The segment is a ring of ringBlocks slots addressed by seq % ringBlocks. The writer publishes blocks at a fixed cadence (periodSeconds = samplesPerBlock / (sampleRateMilliHz / 1000)); the reader keeps a cursor and copies blocks out. The readable window is ringBlocks − 1, never ringBlocks: the writer owns slot head % ringBlocks for the entire current publish period.

writeSeq 0
reader cursor 0
published 0
read 0
dropped 0

What the reader owes the ring (and how it is enforced)

StepRule
0 · at attachInitialise cursor = header.writeSeq, not 0 - starting at 0 reports a spurious multi-million-block overrun on the first read. To read ring history instead, start at head − min(head, ringBlocks − 1).
1 · pick a blockAdvance a local cursor toward writeSeq (acquire load). Unsigned differences only - never < - so the arithmetic survives 64-bit wrap and a cursor briefly seen ahead of head.
2 · overrun checkIf writeSeq − cursor > ringBlocks − 1, the oldest wanted blocks are already recycled: count them as dropped, snap the cursor to the oldest still-readable block.
3 · check before copydesc.seq == wanted seq? Anything else - kSlotBusy or another block's index - means the slot is gone. Count, move on, never spin.
4 · copyCopy payload out into your own buffer. Loop to header.samplesPerBlock from your seqlock snapshot - every published block is full, and attach-time validation has already bounded that field by the plane extent.
5 · check after copyIssue an acquire fence so the copy completes first, then re-read three values and discard the block unless all three still match: desc.seq must equal the wanted seq; header.layoutSeq must equal the snapshot; desc.layoutEpoch must also equal that same snapshot - the layoutEpoch check is the one that defends against stale-geometry aliasing (a block written under a previous geometry can pass the layoutSeq check yet no longer belong to the one you validated).

Two read modes, same protocol:

  • Lossless (Reader::next) - every block in sequence; drops are counted in droppedBlocks(), not hidden.
  • Latest-value-wins (Reader::latest) - only the newest complete block; polling on your own cadence is first-class, not a fallback.
The event is auto-reset, so a configured event means one consumer per stream. Two waiting processes each miss half the wakeups. It is signalled as the last step of a publish and never earlier, so a woken reader always finds writeSeq already advanced - but wakes coalesce, so one wake is not one block once you fall behind: always drain (while (next(b))). Open the event, never create it - CreateEventW on an existing name silently ignores the manual-reset and initial-state arguments. Polling writeSeq carries none of these restrictions and lets several consumers share one segment; derive the poll interval from periodMs, never from a constant.

5 · The layoutSeq seqlock

Layout fields are protected by the layoutSeq seqlock; a producer restart may rewrite them in place. Pinned fields are never rewritten while the segment exists. The seqlock makes changes detectable:

reader:                             producer (start / restart / reconfigure):
  s1 = load(layoutSeq)                next = old + ((old & 1) ? 2 : 1)  // step PAST a leftover odd value
  if (s1 & 1) retry                   store(layoutSeq, next)            // → odd: writing
  copy header (≤ headerBytes)         release_fence()                   // rewrites stay after the odd store
  acquire_fence()                     … rewrite layout fields …
  s2 = load(layoutSeq)                store(layoutSeq, next + 1)        // → even AND strictly greater: done
  if (s1 != s2) retry
  • Odd ⇒ rewrite in progress; even ⇒ stable.
  • A producer restarting into an existing segment MUST cycle the seqlock, even when it rewrites nothing. The bump is the only restart signal a holding consumer gets: it is what triggers re-reading deviceName, re-checking any structural assertion, and knowing that firstSampleIndex restarted at 0 while writeSeq kept running. A leftover odd value - a producer that crashed mid-rewrite - is stepped past, never decremented, so the final value is even and greater than anything a spinning reader has seen.
  • A producer that died mid-rewrite therefore leaves layoutSeq odd, and an attaching consumer sees NotReady on every retry until a producer restarts into the segment. That is not a consumer error.
  • The reader re-checks layoutSeq on every read cycle, not only at attach. It is free - the whole hot range [80, 112) sits in one cache line (64–127), so the load rides along with the writeSeq fetch that was happening anyway.
  • When copying, never copy more than headerBytes: a v1.0 reader facing a larger v1.1 header clamps rather than trusts sizeof.
  • The snapshot's bytes in [80, 112) are meaningless. The concurrent fields change on every publish with no layoutSeq movement, so those bytes may be mid-store garbage in a valid snapshot. Take concurrent values from live per-field acquire loads only.

The stream rate is one of eleven values, 48000 / 2^k for k = 0…10, each half the one above. * publishHz is a bound on the current producer, not on the format - it is the producer's render cadence that sets it, and a later producer may publish faster. Derive the period from samplesPerBlock and sampleRateMilliHz; hardcode nothing.

Size classes (normative)

The envelope is checked against a Float32 layout even when the profile uses Int16, so switching sample format does not change the class. A profile that does not fit the requested class fails open() with a log naming the next larger class that would hold it.

Resolved names and handover. The configured shmName and eventName are base names; the producer appends the class suffix before creating the kernel objects:

resolvedShmName   = shmName   + sizeClassSuffix
resolvedEventName = eventName + sizeClassSuffix

A class switch therefore creates a new segment and a new event. Before the new segment is created, any abandoned leftover segment at the old class name (matching magic, deviceGuid, and a stale lastPublishQpc) is stamped Closed and its event is signalled, so a parked consumer on the old name wakes with WaitResult::Closed instead of waiting out a timeout.

Size formulas (producer-side; consumers read the header)

bytesPerSample      = fmt==Int16 ? 2 : 4
channelPlaneBytes   = samplesPerBlock × bytesPerSample
slotPayloadOffset   = sizeof(ShmBlockDesc)        // 64
slotBytes           = align64(64 + channelCount × channelPlaneBytes)
slotArrayOffset     = align64(sizeof(ShmStreamHeader)) // 256
computeTotalSize()  = slotArrayOffset + ringBlocks × slotBytes   // the LIVE footprint
totalBytes          = the chosen size class (256 KiB / 512 KiB / 1 MiB)

header.totalBytes is the size-class size, not the live footprint - normally larger. The bytes between the last slot and totalBytes are unused producer-zeroed padding, as is the padding inside slotBytes and the reserved[] arrays. computeTotalSize(layout) is what the size-class envelope above is checked against.

Derived quantities (consumers and producers)

These are the formulas Reader uses for timing and liveness. Non-C++ bindings should derive the same timeouts from the header fields rather than hard-coding reader internals.

periodSeconds   = samplesPerBlock / (sampleRateMilliHz / 1000)
periodMs        = samplesPerBlock × 1 000 000 / sampleRateMilliHz   // = periodSeconds × 1000
publishHz       = (sampleRateMilliHz / 1000) / samplesPerBlock
ringSeconds     = ringBlocks × periodSeconds
waitTimeoutMs   = max(50, 4 × periodMs)
staleAfterMs    = max(100, 5 × periodMs)

Constants: kWaitTimeoutPeriods = 4.0, kStaleAfterPeriods = 5.0. The floors keep very short periods from producing timeouts no host scheduler can satisfy.

Concurrency facts for foreign bindings

  • Fields are plain integers, not std::atomic<T> - bindings see bytes and hardcode offsets.
  • x86-64 loads/stores are acquire/release in hardware (TSO); the protocol needs no StoreLoad ordering. Windows-on-ARM64 needs real barriers.
  • Acquire loads and release stores alone are not enough for a seqlock: a release fence follows the odd store (layoutSeq, or kSlotBusy in desc.seq), and an acquire fence comes after the copy, before the recheck. See spec/common/seqlock.md, Memory ordering.
  • 64-bit fields must be naturally aligned to be tear-free; a mapping at offset 0 is 64 KB-aligned, so alignment survives.
  • A 32-bit consumer must use an 8-byte atomic load intrinsic (Interlocked.Read / cmpxchg8b) for the 64-bit fields.
